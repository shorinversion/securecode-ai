## Проект 2. Локальный AI-ассистент разработчика для аудита безопасности кода (SecureCode AI)

### 1. Введение и постановка задачи

#### 1.1. Контекст

Безопасность кода (DevSecOps) критически важна. Утечки API-ключей, SQL-инъекции и уязвимости в зависимостях могут привести к миллиардным убыткам и репутационным потерям компаний.

#### 1.2. Проблема

Стандартные статические анализаторы (SAST) работают по жестким правилам (regex), выдают лавину ложных срабатываний и не понимают контекста логики. При этом отправлять приватный код компании в публичные облачные API (OpenAI) строго запрещено политикой безопасности.

#### 1.3. Предлагаемое решение

Создать локальную систему (на базе квантованной open-source LLM), которая анализирует код «в контексте», находит логические уязвимости и автоматически предлагает безопасные варианты исправления (Auto-Fix patches).

Пример сценария: разработчик пишет метод авторизации и случайно оставляет уязвимый SQL-запрос. Локальный ассистент анализирует код, подсвечивает уязвимый участок и предлагает pull request с исправленным кодом, использующим параметризованный запрос.

### 2. Цели и задачи проекта

#### 2.1. Основная цель

Разработать прототип локального программного комплекса, способного принимать на вход файлы с исходным кодом, проводить семантический аудит уязвимостей безопасности и генерировать патчи для их исправления.

#### 2.2. Ключевые задачи

- Разработать библиотеку инструментов парсинга (Tools): создать Python-функции для построения абстрактного синтаксического дерева (AST), поиска хардкода секретов и уязвимых версий библиотек.
- Определить единый интерфейс для инструментов: задать общий контракт передачи фрагментов кода, метаданных об уязвимостях (CWE ID) и строк файлов.
- Реализовать ядро агентской системы: настроить мультиагентную систему, работающую локально с LLM.
- Определить роли агентов: создать агента Аудитора (ищет потенциальные уязвимости в логике кода) и агента Архитектора (пишет безопасный рефакторинг и проверяет синтаксическую корректность патча).
- Разработать модуль генерации отчета: создать компонент, генерирующий структурированный отчет об уязвимостях с готовыми diff-файлами (патчами) для применения.

### 3. Архитектура системы

Система будет состоять из следующих ключевых модулей:

- Модуль загрузки данных: считывает файлы исходного кода (Python/JS/Go) из локального репозитория проекта.
- Библиотека аналитических инструментов (Tools Library): набор функций (на базе `ast` или `tree-sitter`) для синтаксического анализа кода, поиска паттернов известных уязвимостей и валидации сгенерированного кода.
- Оркестратор агентов (Agent Orchestrator): локальное ядро, координирующее итеративный аудит кода агентами с использованием LLM-сервера.
- Модуль генерации отчетов: компонент, формирующий итоговый `.md`/`.html`-файл с классификацией найденных рисков по стандарту OWASP Top 10 и кодом безопасных исправлений.

### Ожидаемые артефакты

К концу проекта должны быть:

- рабочий прототип локального мультиагентного комплекса с ролями Аудитор и Архитектор;
- библиотека инструментов парсинга (Tools) на базе `ast` или `tree-sitter`: построение AST, поиск хардкода секретов, детекция уязвимых версий библиотек, валидация сгенерированного кода;
- модуль загрузки исходного кода из локального репозитория (Python/JS/Go);
- единый контракт передачи фрагментов кода, метаданных об уязвимостях (CWE ID) и строк файлов;
- модуль автоматической генерации патчей (Auto-Fix) в формате diff-файлов;
- структурированный отчёт `.md`/`.html` с классификацией найденных рисков по OWASP Top 10 и готовыми безопасными исправлениями;
- документация, unit-тесты и пример notebook с прогоном аудита на демонстрационном уязвимом коде.

демонстрации продолжительностью 2–5 минут. Ссылка на развёрнутый сервис
прикладывается при наличии возможности.

## Отделение baseline от развития проекта

После получения задания были согласованы направления развития, которые расширяют baseline, но не подменяют его:

- LLM-слой становится provider-agnostic: `base_url`, `api_key` и `model` задаются через окружение; локальный сервер остаётся поддерживаемым вариантом, но не единственным.
- Основной корпоративный интерфейс — интеграция с GitHub/GitLab: комментарии в PR/MR, check/status и настраиваемая блокирующая CI-job.
- Предусматривается отдельная CLI для локального и CI-запуска; она должна уметь работать автономно и через общий backend.
- Анализ строится вокруг evidence graph, а агентский процесс — вокруг явного workflow graph и ограниченных бюджетом harness loops.
- Любой Auto-Fix считается кандидатом до прохождения детерминированной валидации и, для рискованных изменений, human approval.
